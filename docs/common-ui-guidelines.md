# 공통 UI/디자인 작업 기준

Family Platform의 모든 화면은 공통 디자인 기준을 우선한다. 화면별로 비슷한 UI를 새로 만들지 말고, 기존 공통 클래스와 구조를 재사용한다.

전체적인 디자인 구성은 다른 화면과 동일하게 맞춘다. 버튼 크기, 버튼 높이, 간격, 라벨 위치, 입력칸 높이, radius, 색상은 기존 공통 디자인과 같은 사이즈와 톤을 기준으로 작업하고, 주변 UI와 어긋나는 화면별 임의 디자인을 만들지 않는다.

## 작업 시작 전 확인

- 수정할 화면과 동일한 유형의 기존 화면을 먼저 찾는다.
- 가계부, 캘린더 화면의 필터, 입력폼, datepicker, 목록 패턴을 우선 기준으로 삼는다.
- 기존 공통 클래스가 있으면 새 클래스를 만들지 말고 해당 구조를 사용한다.
- 새 UI가 꼭 필요하면 화면 전용 스타일이 아니라 다른 화면에서도 재사용 가능한 공통 클래스/패턴으로 만든다.

## 공통 클래스 기준

- 조회/필터 영역: `filter-panel`
- 날짜 선택 필드: `date-picker-field`
- 날짜 선택 버튼: `date-picker-trigger`
- 입력 라벨: `form-field`, `form-label`
- 입력 컨트롤: `form-control`
- 폼 레이아웃: `ledger-form` 또는 기존 화면의 공통 form grid 패턴
- 패널 헤더: `panel-header`
- 개수/상태 칩: `passive-header-chip`
- 저장 버튼: `submit-action`, `save-button`
- 취소 버튼: `cancel-button`
- 위험 작업 버튼: `danger-button`, `danger-action`

위 클래스가 이미 있는 경우, 화면별 별도 스타일로 모양을 다시 만들지 않는다.

버튼을 추가할 때는 같은 화면 또는 유사 화면의 기존 버튼 높이, padding, border-radius, 색상, font-weight를 먼저 확인한다. 별도 버튼 클래스를 만들기 전에 `submit-action`, `save-button`, `cancel-button`, `danger-button`, `segmented-control` 같은 기존 공통 버튼 패턴으로 맞출 수 있는지 확인한다.

## 버튼/액션 UI 기준

- 버튼, 링크, 액션 UI는 실제 기능과 이벤트가 연결되어 있을 때만 렌더링한다.
- 스크롤 이동, 포커스 이동처럼 실제 생성/수정/삭제/조회/이동 기능으로 이어지지 않는 버튼은 만들지 않는다.
- 기능이 아직 준비되지 않은 버튼을 자리만 잡기 위해 미리 렌더링하지 않는다.
- 기존에 남아 있는 보여주기식 버튼은 `display: none`으로 숨기지 말고 렌더링 소스에서 제거한다.
- 버튼을 추가했다면 클릭 시 실제 동작, API 호출, 화면 전환, 팝업 표시 등 사용자가 기대하는 결과가 있는지 검증한다.

## Datepicker 기준

- datepicker는 공통 `date-picker-field` + `date-picker-trigger` 구조를 사용한다.
- 캘린더 아이콘은 기존 공통 SVG 형태를 그대로 사용한다.
- 날짜 표시는 기존 화면과 동일하게 `YYYY.MM.DD` 형식을 따른다.
- 월별 조회처럼 월만 보여야 하는 경우도 내부 값은 날짜 ISO 값으로 유지하고, 표시만 `YYYY.MM`로 제한한다.
- 캘린더가 열린 상태에서 다른 입력/버튼에 포커스하면 닫혀야 한다.
- 월/년 이동, 년월 클릭 전환 등 기존 공통 datepicker 동작을 깨지 않는다.

## 목록/상세 화면 기준

- 목록 화면은 큰 단위의 목록만 보여준다.
- 목록 항목을 누르면 상세 화면으로 들어가고, 상세 안에서 하위 기록을 순서대로 보여준다.
- 목록 화면에 상세 기록용 버튼이나 상세 입력폼을 섞어 넣지 않는다.
- 같은 큰 단위 데이터가 중복으로 보일 가능성이 있으면 목록에서 하나로 묶고, 상세에서 관련 하위 기록을 순서대로 보여준다.
- 목록/상세 구조를 수정한 뒤에는 반드시 실제 브라우저에서 `목록 진입 -> row 클릭 -> 상세 진입 -> 목록 복귀` 흐름을 직접 클릭 검증한다.
- 목록 진입만 확인하고 작업 완료로 판단하지 않는다. 상세 화면의 입력폼, 지도, 목록 버튼, row 정렬, 가로 스크롤까지 확인한다.
- 운영 반영 전후로 같은 사용자 흐름을 다시 확인하고, 확인하지 않은 단계는 완료된 것으로 말하지 않는다.

## 소스 구조 기준

- 메뉴별 화면과 동작은 가능한 한 메뉴별 파일 또는 컴포넌트 단위로 분리한다.
- 한 파일에 여러 메뉴의 렌더링, 이벤트, API 처리 코드를 계속 추가하지 않는다.
- 수정 범위는 되돌리기 쉬운 단위로 제한하고, 메뉴 하나를 고치기 위해 다른 메뉴 코드가 같이 바뀌지 않게 한다.
- 목록, 상세, 입력폼, 필터, 공통 datepicker 같은 반복 구조는 재사용 가능한 함수/컴포넌트로 분리한다.
- 기존 레거시 파일을 수정해야 하는 경우에도 새 기능이나 큰 변경은 메뉴별 모듈로 분리할 수 있는지 먼저 확인한다.
- 원복이 필요한 상황을 대비해 커밋과 파일 변경 범위가 메뉴 단위로 추적 가능해야 한다.

## 조회 UI 기준

- 월별/기간별 조회는 가계부 스타일을 기준으로 한다.
- 조회 방식 선택은 명확한 버튼/세그먼트 형태로 제공한다.
- 기간별 조회는 시작일/종료일 datepicker를 사용한다.
- 검색 입력이 있으면 날짜 필터 아래 또는 같은 필터 흐름 안에서 자연스럽게 배치한다.
- 조회 결과 개수는 실제 필터 결과 기준으로 갱신한다.

## Confirm 기준

- 저장, 수정, 삭제처럼 데이터가 생성/변경/삭제되는 버튼은 실행 전에 반드시 공통 confirm을 띄운다.
- 화면별로 `window.confirm`, 임의 confirm UI, 별도 팝업을 새로 만들지 않는다.
- 기존 공통 confirm 컴포넌트/헬퍼가 있으면 반드시 그걸 사용한다.
- 공통 confirm이 없는 경우에는 메뉴별 임시 confirm을 만들지 말고 공통 confirm을 먼저 만든 뒤 모든 메뉴에서 재사용한다.
- confirm 문구는 작업 결과가 명확하게 보이도록 작성한다. 예: 저장하시겠습니까, 삭제하시겠습니까.
- 조회, 목록 이동, 상세 이동, 입력 포커스 같은 읽기 전용 동작에는 confirm을 붙이지 않는다.

## 금지 사항

- 공통 디자인이 있는데 화면별로 임의 색상, border-radius, SVG, spacing을 새로 만들지 않는다.
- `display: none`으로 필요 없는 UI를 숨겨 해결하지 않는다.
- 더미/하드코딩 데이터가 운영 화면에 보이게 하지 않는다.
- 기존 공통 datepicker와 다른 캘린더 모양을 만들지 않는다.
- 목록 화면에 상세 화면 요소를 같이 노출하지 않는다.
- 이벤트가 없거나 실제 기능으로 이어지지 않는 보여주기식 버튼, 링크, 액션 UI를 렌더링하지 않는다.
- 저장/수정/삭제에 화면별 임시 confirm, 브라우저 기본 confirm, 메뉴 전용 confirm을 만들지 않는다.

## 검증 기준

- PC, 태블릿, 모바일, 앱 환경에서 화면을 확인한다.
- 모든 화면 크기에서 텍스트/버튼/입력칸 겹침이 없어야 한다.
- 버튼 크기, 입력칸 높이, 필터 배치가 주변 화면과 같은 디자인 체계로 보여야 한다.
- 가로 스크롤이 생기면 실패로 본다.
- datepicker 열기, 월/년 이동, 날짜 선택, 외부 포커스 닫힘을 확인한다.
- 목록 클릭 시 상세 화면으로 전환되고, 상세 기록이 의도한 순서로 보이는지 확인한다.
- 목록/상세 화면은 목록 진입, row 클릭, 상세 표시, 목록 복귀까지 실제 클릭으로 검증한다.
- 검증은 DOM 개수만 보지 말고 캡처 또는 화면 상태로 디자인 깨짐 여부까지 확인한다.
- 버튼을 추가하거나 수정한 경우 클릭 시 실제 기능이 실행되는지 확인한다.
- 저장/수정/삭제를 변경한 경우 API 결과와 화면 갱신까지 확인한다.
- 저장/수정/삭제를 변경한 경우 공통 confirm이 먼저 뜨고, 확인 후에만 API가 실행되는지 확인한다.
