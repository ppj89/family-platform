# 공통 UI/디자인 작업 기준

Family Platform의 모든 화면은 공통 디자인 기준을 우선한다. 화면별로 비슷한 UI를 새로 만들지 말고, 기존 공통 클래스와 구조를 재사용한다.

## 작업 시작 전 확인

- 수정할 화면과 동일한 유형의 기존 화면을 먼저 찾는다.
- 가계부, 캘린더 화면의 필터, 입력폼, datepicker, 목록 패턴을 우선 기준으로 삼는다.
- 기존 공통 클래스가 있으면 새 클래스를 만들지 말고 해당 구조를 사용한다.
- 새 UI가 꼭 필요하면 화면 전용 스타일이 아니라 다른 화면에서도 재사용 가능한 공통 클래스/패턴으로 만든다.

## 공통 클래스 기준

- 조회/필터 영역: `filter-panel`
- 날짜 선택 필드: `date-picker-field`
- 날짜 선택 버튼: `date-picker-trigger`
- 입력 라벨: `form-field`, `form-label`
- 입력 컨트롤: `form-control`
- 폼 레이아웃: `ledger-form` 또는 기존 화면의 공통 form grid 패턴
- 패널 헤더: `panel-header`
- 개수/상태 칩: `passive-header-chip`
- 저장 버튼: `submit-action`, `save-button`
- 취소 버튼: `cancel-button`
- 위험 작업 버튼: `danger-button`, `danger-action`

위 클래스가 이미 있는 경우, 화면별 별도 스타일로 모양을 다시 만들지 않는다.

## Datepicker 기준

- datepicker는 공통 `date-picker-field` + `date-picker-trigger` 구조를 사용한다.
- 캘린더 아이콘은 기존 공통 SVG 형태를 그대로 사용한다.
- 날짜 표시는 기존 화면과 동일하게 `YYYY.MM.DD` 형식을 따른다.
- 월별 조회처럼 월만 보여야 하는 경우도 내부 값은 날짜 ISO 값으로 유지하고, 표시만 `YYYY.MM`로 제한한다.
- 캘린더가 열린 상태에서 다른 입력/버튼에 포커스하면 닫혀야 한다.
- 월/년 이동, 년월 클릭 전환 등 기존 공통 datepicker 동작을 깨지 않는다.

## 목록/상세 화면 기준

- 목록 화면은 큰 단위의 목록만 보여준다.
- 목록 항목을 누르면 상세 화면으로 들어가고, 상세 안에서 하위 기록을 순서대로 보여준다.
- 목록 화면에 상세 기록용 버튼이나 상세 입력폼을 섞어 넣지 않는다.
- 같은 큰 단위 데이터가 중복으로 보일 가능성이 있으면 목록에서 하나로 묶고, 상세에서 관련 하위 기록을 순서대로 보여준다.

## 조회 UI 기준

- 월별/기간별 조회는 가계부 스타일을 기준으로 한다.
- 조회 방식 선택은 명확한 버튼/세그먼트 형태로 제공한다.
- 기간별 조회는 시작일/종료일 datepicker를 사용한다.
- 검색 입력이 있으면 날짜 필터 아래 또는 같은 필터 흐름 안에서 자연스럽게 배치한다.
- 조회 결과 개수는 실제 필터 결과 기준으로 갱신한다.

## 금지 사항

- 공통 디자인이 있는데 화면별로 임의 색상, border-radius, SVG, spacing을 새로 만들지 않는다.
- `display: none`으로 필요 없는 UI를 숨겨 해결하지 않는다.
- 더미/하드코딩 데이터가 운영 화면에 보이게 하지 않는다.
- 기존 공통 datepicker와 다른 캘린더 모양을 만들지 않는다.
- 목록 화면에 상세 화면 요소를 같이 노출하지 않는다.

## 검증 기준

- 데스크톱, 태블릿, 모바일에서 텍스트/버튼/입력칸 겹침이 없어야 한다.
- 가로 스크롤이 생기면 실패로 본다.
- datepicker 열기, 월/년 이동, 날짜 선택, 외부 포커스 닫힘을 확인한다.
- 목록 클릭 시 상세 화면으로 전환되고, 상세 기록이 의도한 순서로 보이는지 확인한다.
- 저장/수정/삭제를 변경한 경우 API 결과와 화면 갱신까지 확인한다.
